# 실시간 PID 실습

:::part theory

:::note
**이 장의 목표**
- Kp, Kd, Ki가 응답에 주는 영향을 실측(또는 시뮬레이션)으로 설명한다
- 미분 킥과 적분 와인드업을 재현하고 대책(측정값 미분, 포화 중 적분 정지)을 설명한다
- 예측과 실측의 차이를 정량화하고 그 원인에 대한 가설을 세운다
:::

## 들어가기

04장에서 근궤적으로 게인을 계산했고, 05장에서 센서 필터와 지연이 위상여유를 깎는다는 것을 보았습니다. 이제 실제 장치에서 PID를 돌려 봅니다.

오늘의 질문: **"설계에서 예측한 응답과 실제 공의 움직임은 얼마나 같은가? 다르다면 어디서 다른가?"**

이 챕터의 결과물은 두 가지입니다. (1) 여러 번의 시도 끝에 정한 "이 장치의 PID"와 그 근거(시도 이력 표), (2) 예측과 실측이 다른 이유에 대한 **가설**. 두 번째가 07장의 출발점입니다.

## 1. 시스템 구조: 제어 루프는 브라우저에 있다

```
아두이노                                   브라우저(웹 앱)
 초음파 측정(60 ms) → 필터 → D 줄 전송  ──►  y 수신 → 제어기 계산 u
 서보 각도 적용 ◄── S 명령 수신          ◄──  u(rad) → 0.01° 단위로 변환 → S 전송
```

- 아두이노는 60 ms마다 거리(원측정, 필터 출력), 직전에 적용한 서보 명령, 포텐쇼미터 값을 한 줄(`D` 줄)로 보냅니다.
- 브라우저는 그 줄을 받을 때마다 제어기를 한 번 계산하고 서보 명령(`S` 줄)을 돌려보냅니다. 제어 주기는 **장치의 측정 시각**으로 정해집니다.
- **안전 장치**: 각도는 펌웨어가 ±30°(실습에서는 더 작게)로 제한합니다. 브라우저 명령이 500 ms 동안 오지 않으면(탭 닫힘, 케이블 빠짐) 아두이노가 스스로 빔을 수평으로 돌립니다. 화면의 `비상 정지`는 언제나 즉시 작동합니다.

![한 제어 주기의 흐름. 아두이노가 60 ms마다 측정·필터 후 D 줄을 보내면 브라우저가 제어기를 계산해 S 줄로 명령을 돌려보내고 아두이노가 서보에 적용한다. 측정에서 명령까지 약 5~10 ms](assets/06-realtime-pid/loop-timing.svg "그림 1. 한 제어 주기: 측정 → D 줄 → 제어기 계산 → S 줄 → 서보 적용. 다음 측정까지 60 ms 동안 공 위치는 모른다.")

**이 시스템에서의 의미**: 측정 → 계산 → 명령까지 대략 5~10 ms가 걸리고, 그동안 공은 계속 움직입니다. 05장의 지연 표에 이 값이 들어 있었습니다.

## 2. 디지털 PID

슬라이드 62의 의사 코드는 PID의 핵심을 보여 줍니다 [슬라이드 62].

```
error = setPoint - input
cumError += error * elapsedTime        // 적분
rateError = (error - lastError) / elapsedTime   // 미분
out = kp*error + ki*cumError + kd*rateError
```

이 교재의 PID는 같은 생각에 실제 장치에서 꼭 필요한 처리를 더했습니다.

| 처리 | 이유 |
|---|---|
| 실제 측정 간격 $dt$ 사용 | 측정 주기가 조금씩 흔들림 |
| 미분에 1차 필터(`n_filt`) | 3 mm 분해능 잡음을 미분하면 큰 값이 튀므로 |
| 미분을 측정값에(`d_on = measurement`) | 설정값이 바뀌는 순간의 "미분 킥" 방지(4절), 04장의 영점 문제 해결 |
| 출력 제한 + 조건부 적분 | 적분 와인드업 방지(5절) |
| 측정 유실 시 직전 출력 유지 | 센서가 공을 놓친 샘플에서 엉뚱한 명령을 내지 않게 |

### 2.1 단위: 게인 1이 뜻하는 것

이 교재의 게인은 SI 단위입니다. $K_p$ = 1 rad/m는 **공이 목표에서 1 cm 벗어나면 빔(서보 명령)을 0.57° 기울인다**는 뜻입니다.

:::warning
슬라이드 63의 아두이노 코드(`PID_v1` 라이브러리)는 거리를 **cm**, 출력을 **도(°)** 로 계산했습니다 [슬라이드 63, 64]. 그 코드의 $K_p$ = 2.5는 2.5 °/cm이고, SI로는 2.5 × 1.745 ≈ 4.36 rad/m입니다. 기존 실험의 게인이 어떤 단위였는지는 확실하지 않으므로, 슬라이드나 기존 엑셀 데이터의 게인 숫자를 그대로 이 앱에 넣으면 전혀 다른 제어기가 될 수 있습니다. 첫 시도는 반드시 아래 안전 기본값으로 시작하세요.
:::

## 3. 실험 순서: P → PD → PID

:::predict p1
안전 기본값 PD($K_p$ = 1.0, $K_d$ = 1.5, 미분은 측정값에)로 표준 스텝(150 → 200 mm)을 주면 오버슈트는 몇 %일까요? 04장 식으로 $\zeta$를 계산해 예측하고, 실제(또는 가상 장치) 결과가 그 예측보다 클지 작을지도 적어 두세요.
:::

### 3.1 P만 (가상 장치에서만)

03~04장에서 본 것처럼 P만으로는 극점이 허수축 위에 있고, 지연이 조금만 있어도 진동이 **커집니다**. 실제 장치에서는 공이 빔 끝으로 튕겨 나가므로 이 단계는 **가상 장치로만** 해 봅니다. $K_d$ = 0, $K_p$ = 1로 실행해 진동이 줄지 않는(또는 커지는) 것을 확인하세요.

### 3.2 PD (실제 장치 시작)

안전 기본값으로 시작합니다. 시도할 때마다 **한 번에 하나의 값만** 바꾸세요. 그래야 무엇이 효과를 냈는지 알 수 있습니다.

- $K_d$를 키우면 → 감쇠 증가, 오버슈트 감소(너무 크면 잡음이 서보를 떨게 함)
- $K_p$를 키우면 → 빨라짐, 그러나 05장대로 지연여유가 줄어듦

### 3.3 PID

PD 결과에서 목표 근처에 공이 멈춰 오차가 남는다면(03장의 마찰) 작은 $K_i$를 더해 봅니다.

## 4. 미분 킥

설정값이 150에서 200 mm로 갑자기 바뀌면 오차 $e$도 한 샘플 만에 50 mm 뜁니다. 미분을 오차에 걸면 $\dot e$가 순간적으로 매우 커서 서보 명령이 한 번 크게 튑니다. 이것이 미분 킥입니다.

![설정값이 계단으로 바뀌는 순간, 미분을 오차에 걸면 서보 명령이 한 번 크게 튀어 한계에 닿고(빨간 점선), 미분을 측정값에 걸면 명령이 매끄럽게 변한다(파란 실선)](assets/06-realtime-pid/d-kick.svg "그림 2. 미분 킥 개념도: d_on = error는 스텝 순간 명령이 튄다(개념도, 측정값 아님).")

:::predict p2
`d_on`을 `measurement`에서 `error`로 바꾸면 스텝 직후 서보 명령 그래프(u)에 어떤 모양이 나타날까요?
:::

가상 장치에서 두 설정을 비교해 보세요. 실기에서는 미분 킥이 서보와 기어에 충격을 주므로 `error`를 굳이 시험하지 않아도 됩니다.

## 5. 실패 사례: 적분 와인드업

서보 명령이 각도 한계에 닿아 있는 동안에도 오차가 계속 쌓이면, 적분 항이 엄청나게 커집니다. 공이 목표에 도착해도 쌓인 적분이 풀릴 때까지 빔이 반대로 돌아오지 않아 **크게 지나칩니다**.

![위 그래프는 설정값이 바뀐 뒤 공 위치로, 와인드업이 있으면(빨간 점선) 크게 지나치고 포화 중 적분을 멈추면(파란 실선) 덜 지나친다. 아래 그래프는 서보 명령이 각도 한계에 붙어 있는 구간을 음영으로 표시했다](assets/06-realtime-pid/windup.svg "그림 3. 적분 와인드업 개념도: 명령이 한계에 붙은 동안 쌓인 적분이 큰 오버슈트를 만든다(개념도, 측정값 아님).")

:::predict p3
$K_i$를 1.0(안전 기본값의 범위 상한)으로 키우면 오버슈트는 어떻게 될까요? 각도 한계가 작을수록 더 나빠질까요, 좋아질까요?
:::

**가상 장치에서 먼저** 해 보세요: $K_i$ = 0 → 0.3 → 1.0. 서보 명령(u)이 한계에 붙어 있는 시간과 오버슈트를 기록합니다. 디버그 표시를 켜면 P, I, D 각 항의 값을 따로 볼 수 있어, 어느 항이 명령을 지배하는지 보입니다. 이 교재의 PID는 포화 중 적분을 멈추는 장치가 있지만, 그래도 큰 $K_i$는 느린 극점과 감쇠 감소 때문에 오버슈트를 키웁니다(04장 8절).

:::warning
실제 장치에서 큰 $K_i$를 시험할 때는 각도 한계를 10° 이하로 낮추고, 공이 빔 끝으로 갈 것 같으면 바로 `비상 정지`를 누르세요.
:::

가능한 원인 후보: 서보가 명령각을 따라가는 시간(지연·속도 한계), 센서 필터 지연, $K_b$ 오차(03장), 마찰, 수평 보정 오차. 그래프의 `servo_pot_cdeg`(포텐쇼미터로 읽은 실제 서보 각도)와 `u_cdeg`(명령)를 겹쳐 보면 첫 번째 후보를 직접 확인할 수 있습니다. 실제 각도가 명령보다 얼마나 늦나요?

:::note
**가상 장치와 디지털 트윈의 차이.** 이 장의 가상 장치는 위 점선 예측과 **같은 모델**(서보 무시 선형 모델 + 잡음 + 60 ms 샘플링)로 돕니다. 그래서 가상 장치에서는 "예측과 다르다"가 거의 나타나지 않고, 위의 원인 후보(서보 늦음, 마찰, 수평 오차)를 가상 장치로는 시험할 수 없습니다. 가상 장치는 절차와 화면을 익히는 도구입니다.

21장의 **디지털 트윈**은 설계 모델과 **일부러 다른** 물리(sin 레버, 구름·정지 마찰, 수평 오차, 서보 데드밴드·백래시, PWM 프레임, 센서 이상값·유실)로 돕니다. 같은 PD(1.0, 1.5)가 가정 서보 포함 설계 모델에서는 오버슈트 약 10%(설정값 기준 10.2%, 21장 `step-nominal`의 10 s 관찰 기준 10.9%), 공칭 트윈에서는 41.3%였습니다 `[시뮬레이션]`(21장 `step-nominal` 조건: 스텝 뒤 10 s까지 관찰, 각도 한계 30°. 설계 모델 쪽은 센서 잡음 없음, 트윈 쪽은 센서 잡음 σ 2 mm와 이상값 포함. 트윈 파라미터 `[가정]`, 트윈 기본 despike 0 = 펌웨어 1.0.0 동작). 다만 이 41.3%는 **대부분 스텝 직전(t = 1.99 s)에 나온 센서 이상값 한 개 때문**입니다. 같은 실행에서 이상값을 끄면 10.0%, 펌웨어 1.1.0의 이상값 제거 gate를 켜면 9.4%로 설계 모델과 비슷합니다 `[시뮬레이션]`(`docs/theory/digital-twin.md` §6.4). 그러니 이 숫자를 "트윈에서는 지연 때문에 오버슈트가 약 네 배가 된다"로 읽으면 안 됩니다. 21장 4절에서 직접 확인합니다. 다만 트윈도 실제 장치를 얼마나 닮았는지는 **실측으로 검증하지 않았으므로**, 여러분의 실측을 대신하지 못합니다. 실측이 진짜 기준입니다.
:::
